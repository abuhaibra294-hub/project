# DareCare — اجتماع الفريق | الجمعة 23 أكتوبر 2026

**الغرض:** استعراض تقدم Backend .NET الواقعي، الاتفاق على عقود الـAPI، والخطوات المطلوبة للتكامل مع Flutter والـWeb.

> تنبيه مهم: تم إنشاء الكود وفحص بنية المصادر وملفات JavaScript، لكن لم يتم إجراء dotnet build / dotnet test / SQL Server integration في بيئة إعداد الملفات. **لا نعلن نجاح التشغيل حتى ننفّذ الاختبارات على جهاز Windows أمام الفريق.** البيانات التي يُسمح بعرضها تجريبية بالكامل.

## ملخص تقدم العمل في دقيقة

- تم إعداد حل ASP.NET Core 10 طبقي `Domain / Application / Infrastructure / API` بنمط Modular Monolith وقاعدة SQL Server للمشروع النهائي وSQLite للتجارب المحلية.
- تم إعداد `Identity + JWT + Refresh Token`، وتسجيل عميل وممرض، دعوة صيدلية من الإدارة، تأكيد/استعادة البريد وفق إعداد SMTP، وإغلاق الجلسات وصلاحيات أربعة أدوار.
- يوجد تدفق للممرض: ملف شخصي، مهارات، اعتماد الإدارة، جدول توافر، ترتيب ترشيحات قواعدي، حجز، قبول وبدء وإنهاء الزيارة وإلغاؤها وفق الحالات المسموح بها.
- يوجد تدفق للصيدلية: رفع روشتة خاصة، مراجعة، عرض سعر، موافقة العميل، تجهيز/شحن/تسليم؛ الملف لا يتم نشره للعامة.
- إضافة Sprint 4: مراجعة 1–5 نجوم بعد **زيارة مكتملة** فقط (مرة واحدة لكل زيارة)، متوسط التقييم في نتائج الترشيح، Dashboard مختصر حسب الدور، ومنع ظهور الممرض المعطل في القوائم العامة والحجز.
- كل تغيير مهم له في معظم المسارات إشعار داخلي أو Audit Event؛ لا يوجد دفع حقيقي أو وصفة حقيقية أو توصيل خارجي.

## Demo عملي: 8–10 دقائق

1. **دقيقة 1 — Architecture:** افتح `docs/ARCHITECTURE.md` ومجلد `src` واشرح الفصول الأربعة. نفس الـAPI يستخدمه تطبيق Flutter ولوحات Web.
2. **دقيقة 2 — التشغيل:** فك ZIP، شغّل `START_DARECARE.cmd` وانتظر نجاح البناء والاختبارات وظهور `http://127.0.0.1:5208/dev/auth`، ثم شغّل `DEMO_SESSION.cmd` (لا تعمل الأخيرة إذا فشل التشغيل). تجنب عرض ملفات كلمات المرور على شاشة مشاركة عامة.
3. **دقيقة 3 — Auth & RBAC:** ادخل بحساب عميل تجريبي ثم افتح «بيانات الحساب» و«لوحتي حسب الدور». جرّب `GET /api/v1/admin/overview` بالعميل وشاهد 403؛ ثم ادخل بحساب مدير محلي واستخدم Pending Nurses.
4. **دقيقتان — رعاية وتمريض:** ادخل بممرض تجريبي، ورّهم ملفه ومواعيده؛ ادخل بعميل، افتح الخدمات والترشيحات ثم «حجوزاتي»، وبعدها حالة الزيارة المكتملة؛ جرّب `GET /api/v1/bookings/mine`.
5. **دقيقة — Reviews/Matching (الجديد):** افتح «متوسط تقييم الممرض» بعد تشغيل السيناريو الوهمي. راجع `GET /api/v1/reviews/nurses/{nurseId}/summary` وحقل `averageRating` في `matching/nurses`. إعادة التقييم تؤدي إلى `409 Conflict`.
6. **دقيقتان — الصيدلية:** ادخل بحساب الصيدلية الذي أنشأه سيناريو الـDemo، افتح «طلبات الصيدلية»، ثم ادخل بالعميل وافتح طلباته؛ وضّح أن الصيدلية تصدر عرض السعر والعميل يوافق قبل التجهيز.
7. **دقيقة — الأمان + الفجوات:** اعرض `403` على مورد لا يخص المستخدم، ووضح إن الـRefresh Token يتجدد ويتلغى، وإن رفع الملفات خاص. ثم اذكر أن التحقق التشغيلي والتدقيق الأمني وتكامل الفريق هي العمل التالي.

> **مهم للعرض:** السيناريو الآلي `DEMO_SESSION.cmd` يكمل الطلبات بنفسه وينشئ حسابات **عشوائية وهمية**، فلا تعيد خطوة «تأكيد/تجهيز/تسليم» على نفس الطلب وإلا سترى `409` بشكل صحيح. لعرض خطوات الحالات حيًا أنشئ طلبًا ثانيًا من صفحة التجربة أو شغّل السيناريو مجددًا ببيانات جديدة.

## أوامر وملفات السيشن

- `START_DARECARE.cmd` — تشغيل الباك إند في وضع SQLite للتجربة، مع محاولة تثبيت .NET 10 إن كان غير موجود.
- `DEMO_SESSION.cmd` — مع السيرفر شغال: ينفّذ Smoke Flow ببيانات وهمية، يختبر الأدوار والممرض والتقييم والصيدلية، ويفتح الواجهة وملاحظات العرض.
- `SMOKE_DARECARE.cmd` — تشغيل نفس اختبارات الرحلة من غير كتابة ملف حسابات Demo.
- `TEST_DARECARE.cmd` — بناء + اختبارات الوحدة فقط.
- `START_SQLSERVER.cmd` — SQL Server LocalDB منفصل للبيانات التجريبية؛ لا تشغّل النمطين في نفس الوقت.
- `.localdata/demo-accounts.txt` — حسابات العميل والممرض والصيدلية التي ولّدها `DEMO_SESSION.cmd`، **محلية وسرية حتى لو تجريبية**، لا ترفعها إلى GitHub.
- `.localdata/admin-login.txt` — حساب الإدارة، لا ترسله على الشات أو تشارك كلمة المرور في تسجيل الشاشة.

## API Contracts المطلوبة من Flutter والـFrontend

| الجزء | API |
|---|---|
| تسجيل ودخول | `POST /api/v1/auth/register/patient`, `/register/nurse`, `/login`, `/refresh`, `/logout` |
| حسابي / Dashboard | `GET /api/v1/auth/me`, `GET /api/v1/dashboard/me` |
| الخدمات والممرض | `GET /api/v1/services`, `/nurses`, `/matching/nurses?serviceId=...` |
| الحجوزات | `POST /api/v1/bookings`, `GET /api/v1/bookings/mine`, `POST /api/v1/bookings/{id}/accept` |
| التقييم | `POST /api/v1/reviews/bookings/{bookingId}`, `GET /api/v1/reviews/nurses/{nurseId}/summary` |
| الصيدلية | `POST /api/v1/prescriptions`, `POST /api/v1/orders/prescriptions/{id}/quote`, `POST /api/v1/orders/{id}/confirm` |
| إدارة | `GET /api/v1/admin/overview`, `GET /api/v1/admin/nurses/pending` |

## توزيع عملي على الفريق بعد الاجتماع

- **Backend .NET A:** تثبيت عقود User/Care/Bookings/Reviews، Migration حقيقية لـSQL Server، اختبارات تكامل وقيود مواعيد الزيارة.
- **Backend .NET B:** مراجعة Prescription/Pharmacy Order، رفع/تخزين الملفات وتحصينها، قواعد عمل استبدال الدواء، الإشعارات ومراجعة العقود مع الواجهة.
- **Flutter:** شاشة العميل: Auth وProfile وServices وMatching وBookings وReviews وPharmacy Orders وربطها بـAPI.
- **Web Frontend A:** واجهة الممرض: حسابي/اعتماد/توافر/قبول الزيارات وحالاتها.
- **Web Frontend B:** لوحة الصيدلية والإدارة: Inbox/Quote/Statuses/Approvals/Dashboard.
- **UI/UX:** حالات Loading/Error/Empty/Unauthorized والشاشات الأربع، وتوثيق التصميم Responsive وRTL.
- **Cybersecurity:** اختبار JWT/Refresh وBOLA/IDOR، حماية الملفات، تحليل الثغرات وتهديدات الخصوصية.
- **AI/QA (إن وجد العضو الثامن):** التقييم المنطقي للـmatching ومقارنة الترشيحات، وE2E tests لرحلة المريض.

## الأمور التي لم تكتمل ويجب قولها بوضوح

1. التشغيل على جهاز صاحب المشروع واختبارات `dotnet build` / `dotnet test` / E2E / SQL Server لم تُثبت بعد؛ CI يحتاج التنفيذ والمتابعة.
2. Ranking الحالي قواعد قابلة للتفسير **وليس AI متدرّبًا**. لا يوجد تشخيص طبي.
3. تأكيد الزيارة الميدانية باستخدام OTP/GPS والتوقيت الحقيقي، ومكافحة احتيال التقييمات، وإدارة تضارب الموافقات تحتاج شغلًا إضافيًا.
4. SMTP حقيقي وPush Notifications وتخزين ملفات طبي مشفّر ومسح فيروسات وتكامل Payment/Delivery ليست جاهزة للإنتاج.
5. خطوة التكامل مع واجهات الفريق وGitHub PRs لم تتم في هذه النسخة؛ الشغل الموجود حاليًا ZIP محلي.
