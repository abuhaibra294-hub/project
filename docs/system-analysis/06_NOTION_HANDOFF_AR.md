# DARECARE — مهام عبد المقصود: الوصف ومعايير القبول للتسليم في Notion

> هذه النصوص جاهزة للنسخ في حقلي \`Description\` و\`Acceptance Criteria\`، دون تغيير اسم المهمة أو صاحبها أو تاريخها في Notion. التوثيق تم تحضيره على GitHub، **ولا يعني أن فريق المراجعة اعتمده**. حافظ على \`To Do\` حتى بدء العمل أو استخدم \`In Review\` إن كانت متاحة وبعد التأكد من المخرجات.

## 1) ER Diagram — مخطط الكيانات والعلاقات
**Priority:** High

**Description (انسخ هذا النص):**
> إعداد مخطط ER Diagram لمشروع DARECARE اعتمادًا على كيانات النظام وعلاقات SQL Server الفعلية، مع توضيح الجداول الرئيسية والثانوية، والمفاتيح الأساسية والخارجية، وأنواع العلاقات 1:1 و1:N وM:N عبر الجداول الوسيطة. يشمل مستخدمي النظام، ملفات المرضى والممرضين والصيدليات، الخدمات والمواعيد والحجوزات، الروشتات وطلبات الصيدلية والمراجعات والدعم. يحتوي التسليم على مخططات Mermaid قابلة للتعديل وفهرس كامل للعلاقات.
>
> Deliverable: [ER Diagram](01_ER_DIAGRAM.md)

**Acceptance Criteria (انسخ هذا النص):**
> وجود ERD يغطي جميع الكيانات والعلاقات الموجودة في Migration الحالية (25 جدولًا و35 FK)، مع إظهار cardinality ومفاتيح PK/FK، وتوضيح العلاقات الاختيارية والجداول الوسيطة، ومطابقة الرسم مع EF Core DbContext ثم مراجعة النتائج واعتمادها من مسؤول الـBackend.

## 2) Logical & Physical Schema — المخطط المنطقي والفيزيائي
**Priority:** High

**Description:**
> إعداد Logical Data Model يوضح تنظيم بيانات DARECARE والعلاقات الوظيفية بين الحسابات ومقدمي الخدمة والحجوزات والصيدليات والدعم، وتحويله إلى Physical SQL Server Schema موثق من EF Migration الموجودة. يشمل أسماء الجداول والأعمدة وأنواع SQL وPK/FK والـIndexes والـUnique Constraints والـCheck Constraints والقواعد المرتبطة بالبيانات الحساسة.
>
> Deliverable: [Logical & Physical Schema](02_LOGICAL_PHYSICAL_SCHEMA.md)

**Acceptance Criteria:**
> نموذج منطقي واضح، وبيان فيزيائي كامل لجميع جداول وأعمدة SQL Server الحالية (25 جدولًا، 170 عمودًا، 43 فهرسًا)، وتوثيق كافة المفاتيح والعلاقات والقيود وخصوصية ملفات الروشتات، مع التحقق من مطابقة الـMigration ومراجعة مسؤول قواعد البيانات. تشغيل النشر الدائم اختبار منفصل، وليس شرطًا لتسليم وثيقة المخطط نفسها إلا إن طلب المشرف.

## 3) DFD — مخططات تدفق البيانات
**Priority:** Medium

**Description:**
> إعداد Data Flow Diagrams لمشروع DARECARE، تشمل Context Diagram (Level 0)، وLevel 1 يوضح العمليات الأساسية ومخازن البيانات، ثم Level 2 لرحلتي حجز الرعاية المنزلية ورفع الروشتة وطلب الدواء. توضح الرسومات مدخلات ومخرجات المريض والممرض والصيدلية والإدارة، ومسارات التحقق من الصلاحيات وتخزين البيانات والإشعارات، مع التمييز بين الخدمات الخارجية الاختيارية والمتاح فعليًا.
>
> Deliverable: [Data Flow Diagrams](03_DATA_FLOW_DIAGRAM.md)

**Acceptance Criteria:**
> وجود مخططات DFD بمستويات 0 و1 و2 واضحة ومتوازنة وظيفيًا، توثق الجهات الخارجية والعمليات ومخازن البيانات وتدفق المعلومات في الحجز والروشتات، وتطابق واجهات الـAPI وآليات التخزين الفعلية، دون إضافة أنظمة دفع أو مخزون أو توصيل لم تُنفَّذ.

## 4) Component Diagram — مخطط المكونات
**Priority:** Medium

**Description:**
> إعداد Component Diagram يوضح مكونات النظام البرمجية وعلاقات الاعتماد بينها، بما يشمل تطبيق Flutter وواجهات الويب وASP.NET Core API وطبقات Application وDomain وInfrastructure وقاعدة البيانات، إلى جانب خدمات المصادقة والبريد وتخزين الملفات. يتضمن مخططًا لمراجع المشاريع البرمجية وأمثلة توضح التواصل بين العميل والـBackend.
>
> Deliverable: [Component Diagram](04_COMPONENT_DIAGRAM.md)

**Acceptance Criteria:**
> مخطط مكونات يعكس البنية الحالية للمستودع وليس تصميمًا افتراضيًا، ويظهر حدود الطبقات ومسؤوليات كل جزء واتصالات REST والمصادقة والتخزين، مع شرح الاعتماديات ومراجعة الملفات الحالية في الـSolution واعتماد الرسم من مسؤول الـBackend.

## 5) State Diagram — مخططات الحالات
**Priority:** Medium

**Description:**
> إعداد State Diagrams تصف دورات حياة الحجوزات وطلبات الصيدلية وتذاكر الدعم في نظام DARECARE، بدايةً من الإنشاء وحتى الحالات النهائية، مع توضيح الأحداث التي تنقل الكائن من حالة إلى أخرى، والجهة المخولة بإجراء كل انتقال، والقيود المطبقة في Domain وREST APIs.
>
> Deliverable: [State Diagrams](05_STATE_DIAGRAMS.md)

**Acceptance Criteria:**
> مخططات حالات دقيقة للحجز (Pending/Accepted/InProgress/Completed/Cancelled/Rejected)، وطلبات الدواء (Quoted/Confirmed/Preparing/OutForDelivery/Delivered/Declined)، والدعم (Open/InProgress/Resolved/Closed)، تُظهر الانتقالات المسموحة فقط وتحدد أدوار المستخدمين وأمثلة للانتقالات المرفوضة، مع مطابقة Domain Transition Methods.
